# Bsync replication protocol, version 1

- **Status:** Draft. Message semantics, JSON encoding and the HTTP binding (section 8) are implemented
  (`Bsync.Server.AspNetCore`, `HttpSyncTransport` in `Bsync`) by the in-memory reference authority and the
  PostgreSQL authority (`Bsync.Server.PostgreSql`), and checked by fixtures and by running the authority
  conformance suite in process, through the JSON encoding, over HTTP and on PostgreSQL. Release status:
  [README](../../README.md#status).
- **Fixtures:** [`fixtures/valid`](fixtures/valid) must decode and re-encode to equivalent JSON;
  [`fixtures/invalid`](fixtures/invalid) must be refused. `WireFormatTests` enforces both.
- **Conformance:** `LocalStoreConformance` and `AuthorityConformance` in the `Bsync.Testing` package
  (`src/Bsync/Bsync.Testing`) are the executable form of sections 4–6.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119
and RFC 8174 when, and only when, they appear in all capitals.

## 1. Roles and scope

- A **replica** holds a local copy of one collection for one scope and originates writes.
- The **authority** (server) owns the current state of every document, assigns versions, decides every
  write, and serves the change feed.
- A **collection** is a set of documents of one type, identified by id. Each message in this document is
  exchanged for exactly one collection and one scope; how they are named is part of the binding
  (section 8). The scope is derived by the binding from the authenticated caller, never from a message body
  (section 8, ADR-010); checkpoints are bound to it, and a changed scope is refused with reason `scope-changed`
  (section 6.1).

## 2. Data model

### 2.1 Documents

A document is a JSON object defined by the application. It MUST contain:

| Member | Type | Meaning |
|---|---|---|
| `id` | string | Document id (section 2.2). Immutable. |
| `updatedAt` | string | Origin timestamp (section 2.3) of the current state. |
| `deleted` | boolean | `true` for a tombstone. |

The member names above assume a camelCase naming policy; an application MAY use other names if every
peer uses the same serialization contract. Other members are application data.

A replica that writes a document it received MUST NOT drop members it does not understand; it SHOULD
preserve them (for example with `[JsonExtensionData]`) so that an older client cannot erase fields added
by a newer one (I17). Applications SHOULD encode decimal values and 64-bit integers as strings when
non-.NET peers participate.

### 2.2 Identifiers

Document ids and operation ids are strings of 1–256 UTF-16 code units, with no control characters and
no unpaired surrogates. They are compared ordinally (by UTF-16 code unit). Non-ASCII ids are valid.
Operation ids MUST be globally unique; replicas SHOULD use 128-bit random or time-ordered UUIDs.

### 2.3 Origin timestamps

An origin timestamp is a Hybrid Logical Clock value encoded as
`{wallTime:D15}:{counter:D6}:{node}`, where `wallTime` is Unix milliseconds (0–999,999,999,999,999),
`counter` is 0–999,999 and `node` is empty or 1–64 characters from `[A-Za-z0-9._~-]`. Encoders MUST emit
exactly this form; decoders MUST reject anything else. Ordinal comparison of encodings equals timestamp
order.

The authoring replica stamps `updatedAt`. The authority MUST NOT change it. It is metadata for policies
such as last-write-wins, not a version or a cursor.

### 2.4 Versions

Each committed state of a document has a **version**: a positive 64-bit integer. Versions of one document
strictly increase. Versions are encoded as JSON strings of ASCII digits without sign or leading zeros
(`"9007199254740993"`). Decoders MUST reject numbers, signs, leading zeros and values above 2^63−1.

### 2.5 Checkpoints

A checkpoint is an opaque JSON string issued by the authority, or `null` for the start of the feed.
Replicas MUST store and return it verbatim and MUST NOT parse or construct it.

## 3. Messages

### 3.1 Pull request

```json
{ "checkpoint": null, "limit": 100 }
```

| Member | Required | Meaning |
|---|---|---|
| `checkpoint` | yes | The replica's stored checkpoint, or `null`. |
| `limit` | yes | Maximum number of changes to return, ≥ 1. The authority MAY return fewer. |
| `features` | no | Response features the replica understands, for example `["removals"]`. Authorities ignore unknown values. |
| `replica` | no | An identifier of the replica (its clock node id). Servers MAY record which checkpoint each replica reached (an audit); they MUST NOT change the response because of it. |

### 3.2 Pull response

```json
{
  "changes": [ { "document": { ... }, "version": "42" } ],
  "checkpoint": "…",
  "hasMore": false
}
```

- `changes` contains at most `limit` entries and at most one entry per document id: the document's state
  at the page's position, with its version. Tombstones are included.
- `checkpoint` is the position after the page.
- `hasMore` is `true` when further changes are immediately available. If `hasMore` is `true`, the
  checkpoint MUST differ from the request's checkpoint.
- `features` (optional) lists optional protocol features the authority supports: `"groups"` (section 4.1),
  `"limits"`, `"server-time"`, `"retention"` and `"removals"` (below). Receivers ignore unknown features; an absent member means none.
- `limits` (optional, with feature `"limits"`) is `{ "maxOperationsPerPush": n, "maxPageSize": m }`, both integers
  ≥ 1. A replica SHOULD send at most `maxOperationsPerPush` operations per push and request at most `maxPageSize`
  changes per pull once it has seen them. Before the first pull it uses its own configuration.
- `serverTime` (optional, with feature `"server-time"`) is the server's time in Unix milliseconds, encoded like other
  64-bit values (section 2.4). A replica whose clock is ahead SHOULD correct the physical input of its HLC by the
  difference, without letting timestamps go backwards (ADR-017).
- `retentionHorizon` (optional, with feature `"retention"`) is the version at or below which the authority has purged
  tombstones (section 4), encoded like other 64-bit values; `0` or absent when nothing was purged. A replica MAY drop
  its own tombstones at or below it that have no local changes and no unresolved conflict.
- `removals` (optional, with feature `"removals"`, only when the request listed `"removals"`) lists ids of documents that
  left the caller's view within the page's range (ADR-015). An id appears at most once per page and never in both
  `changes` and `removals`; together they count against `limit`. A replica MUST remove clean copies (never deleting
  anything on the server) and MUST keep copies with local changes or unresolved conflicts, hidden. An authority that would
  need a removal for a request without `"removals"` MUST answer `reset-required` with reason `scope-changed` instead.

### 3.3 Push request

```json
{
  "operations": [
    { "operationId": "…", "documentId": "n1", "baseVersion": null, "document": { ... } }
  ]
}
```

| Member | Required | Meaning |
|---|---|---|
| `operationId` | yes | Id of this logical write (section 5). |
| `documentId` | yes | Equal to `document.id`. |
| `baseVersion` | yes, may be `null` | The version the write was based on; `null` if the replica believes the document is new. |
| `document` | yes | The complete new state (or tombstone). |
| `group` | no | Dependency group id (section 4.1). |
| `groupSize` | with `group` | The number of operations of that group in this request (a JSON number). |

A request MUST contain at most one operation per document id. Operations without a `group` are
**independent**: there is no batch atomicity, and the authority MAY accept some and not others.

### 3.4 Push response

```json
{ "outcomes": [ { "operationId": "…", "kind": "accepted", "version": "43", "document": { ... } } ] }
```

| Member | Present when | Meaning |
|---|---|---|
| `operationId` | always | The operation this outcome answers. |
| `kind` | always | `accepted`, `conflict`, `rejected` or `retry-later`. Decoders MUST reject other values and numbers. |
| `version` | `accepted`, `conflict` | The version after acceptance, or the current version on conflict. |
| `document` | `accepted`, `conflict` | The authoritative state after acceptance, or the current state on conflict. |
| `errorCode` | `rejected`, `retry-later` | Machine-readable reason (section 7). |
| `message` | optional | Human-readable detail. Not localized. |
| `arguments` | optional | An object of string values that complete `errorCode` for a UI, for example `{ "max": "200" }`. Keys are chosen by the authority and stable like codes. A replayed outcome carries the same arguments. Replicas that do not know the member ignore it. |
| `duplicate` | optional, default `false` | `true` when the authority is replaying a stored outcome. |

## 4. Authority rules (push)

For each operation, in request order, the authority MUST:

1. Reject with `invalid` an operation whose ids are invalid, whose `documentId` differs from
   `document.id`, whose `baseVersion` is not `null` and < 1, or whose document already has an operation in
   the same request.
2. If a receipt exists for `operationId`: if the stored request fingerprint (document id, base version and
   canonical document) is equal, return the stored outcome with `duplicate: true` and change nothing;
   otherwise reject with `operation-id-reused` and change nothing.
3. Reject with `clock-skew` if `document.updatedAt` is more than the configured skew ahead of authority
   time.
4. Apply application validation and authorization; reject with their error code if refused.
5. **Conditional write.** If the document exists and `baseVersion` differs from its current version
   (including `null` against an existing document), return `conflict` with the current state and version.
   Otherwise commit the document with a new version.
6. Store a receipt with the outcome of steps 3–5 in the same transaction as any write (I04). Rejections
   in steps 1–2 are not stored.

Steps 5 and 6 MUST be atomic with respect to concurrent operations on the same document (I05).

If the document does not exist, step 5 accepts the write whatever its `baseVersion`, with one exception: if
the authority has purged tombstones up to a **retention horizon** and `baseVersion` is at or below it, the
document may have been deleted and purged, so the write is rejected with `base-expired` instead of
resurrecting it. A replica that receives `base-expired` forgets its base; writing the document again
(`baseVersion: null`) recreates it explicitly. After a restore, a replica may hold a pending edit based on
state the restore lost; accepting it preserves that edit. This is safe only because of the version rule in
section 6.1: a base version can never accidentally equal the version of a different state.

Receipts SHOULD be retained at least as long as a replica may resend the operation. An authority MAY expire
receipts of accepted operations. A replay after its receipt expired is then decided by step 5: the accepted
write changed the version, so the replay's base no longer matches and the answer is `conflict`. The
operation is never applied twice, but the replica's conflict policy runs for a write that had succeeded.

### 4.1 Dependency groups

Operations that carry the same `group` form a **dependency group**. They are applied all together or not at
all. An authority that supports groups advertises `"groups"` in pull responses (section 3.2), and a replica
MUST NOT send `group` to an authority that does not. An older authority would ignore the member and apply
the operations independently.

The authority MUST:

1. Reject every operation of the group with `invalid` if the group id is not a valid identifier, if the number
   of operations carrying the group in the request differs from any member's `groupSize`, or if a member is
   malformed. Such rejections store no receipt.
2. Decide every member as in section 4 (replaying stored receipts), without committing anything yet.
3. If every member would be accepted (or replays an acceptance), commit all of them, with their receipts,
   atomically.
4. Otherwise commit none of them. A member that was decided `conflict` or `rejected` keeps that outcome, and its
   receipt is stored. Every other member gets `retry-later` with `errorCode` `group-aborted` and **no** receipt:
   it was not decided, and a resend with the same operation id is decided afresh.

The operation fingerprint (section 4, step 2) includes `group` and `groupSize`.

Replica rules:

- All members of a group are sent in one request, even if that exceeds the replica's batch size.
- A member answered `group-aborted` stays pending unchanged.
- When a member conflicts:
  - If the conflict policy produces a new change, the group is resent with it.
  - If the conflict is kept for the user, settled with the server state, or rejected, the other members are
    parked locally with `group-failed`.
  - Resolving or retrying that member releases them.
- If the group's membership changes before it is sent, the replica replaces the members' pending operations
  with new ones. This is safe: an operation that may already have been applied carries a base version that no
  longer matches, so its replacement conflicts rather than applying twice.

## 5. Replica rules (push)

- A replica MUST persist an operation (id, base version, exact payload) before sending it, and MUST resend
  exactly the same operation until it receives a final outcome (`accepted`, `conflict`, `rejected`).
- A transport failure, cancellation, timeout, `retry-later` outcome or missing outcome means the result is
  unknown; the operation MUST be kept and resent later with the same id.
- A replica MUST refuse (and apply nothing from) a response that contains an outcome for an operation it
  did not send, two outcomes for one operation, an unknown `kind`, or an `accepted`/`conflict` outcome
  without a document and version for the right document id.
- On `accepted`, the replica adopts the returned version as its base. Its local state becomes clean only
  if no later local edit exists; a later edit stays pending on the new base (I02).
- On `conflict`, the replica resolves with its policy using the returned state and version as the new base.
- On `rejected`, the replica parks the record and MUST NOT resend it until a new local edit exists (I19).
- Unsent local edits of one document coalesce into one operation. Once persisted, an operation is
  immutable.

## 6. Feed rules (pull)

- Every checkpoint MUST denote a committed, gap-free prefix of the feed: no change that commits later may
  appear at or before an already-issued checkpoint (I06).
- A replica MUST apply a page's changes and store its checkpoint atomically (I03), MUST refuse a page with
  duplicate document ids or more than `limit` changes, and MUST refuse a page with `hasMore: true` that
  does not advance the checkpoint.
- A replica MUST NOT replace a state with an equal or lower version (I09).
- A replica with unconfirmed local changes to a document keeps its local state and base, and remembers the
  newer server state, which it adopts if its own change later settles on an older version.
- A checkpoint issued by a different authority history (epoch) MUST be refused with a reset requirement.

### 6.1 Epochs, restores and reset

Authority rules:

- The authority MUST start a new epoch whenever part of its history may have been lost (restore from a
  backup, failover to a lagging replica, manual repair). Checkpoints from an older epoch MUST be refused with
  `reset-required`.
- The authority MUST NOT issue a version it may already have issued for a different state, in any epoch.
  After a restore it MUST continue above the highest version the lost history may have issued (for example
  by advancing the sequence by a safety margin or embedding the epoch in the version). Operation receipts
  restored from the backup MUST be kept.

A checkpoint MUST also be refused with `reset-required` when what the caller may see changed since it was
issued (permissions, filter; reason `scope-changed`), or when it is older than the retention horizon (reason
`expired`). The reason tells the replica what to do with records the new snapshot does not contain:

| Reason | Meaning | Records absent from the new snapshot |
|---|---|---|
| `epoch` (also when absent or unknown) | The history changed (restore, failover). | Hidden and kept (**missing after reset**). |
| `scope-changed` | The caller's visible set changed. | Removed from the device (never deleted on the server). |
| `expired` | Retention removed history the replica needs. | Removed from the device. |

Replica rules, when a pull is refused with `reset-required` and the stored checkpoint is not the start:

1. Atomically increment the replica **generation**, set the checkpoint to the start and enter resnapshot
   mode. Records, pending operations and rejections are not modified.
2. Pull from the start. Versions are compared only within one generation: a change for a record last
   confirmed in an older generation replaces a clean record even if its version is lower. Records with
   unconfirmed local changes keep their state; the server state is remembered as observed.
3. When the snapshot completes, every clean record not confirmed in the new generation is marked **missing
   after reset** (hidden from queries, kept for inspection, not propagated as a deletion) or, for
   `scope-changed` and `expired`, removed. A record with unconfirmed local changes or an unresolved conflict is
   never removed; it is marked missing instead. A later pull or local write of the same id clears the mark.
   Then leave resnapshot mode.
4. Pending operations are resent unchanged (same id and payload). The authority replays a receipt it still
   has, accepts the write if the document no longer exists, and otherwise answers with a conflict unless
   the base version names its current state.

Each step commits atomically; after a crash the replica resumes in resnapshot mode from its last committed
checkpoint and repeats the sweep, which is idempotent. A reset required while the checkpoint is already the
start is an error and is not retried.

## 7. Error codes

| Code | Where | Meaning | Replica action |
|---|---|---|---|
| `invalid` | outcome | Malformed operation. | Park; fix the application. |
| `operation-id-reused` | outcome | Same id, different request. | Park; indicates a replica bug. |
| `clock-skew` | outcome | Origin timestamp too far in the future. | Park until a new edit with a correct clock. |
| `forbidden` | outcome | Not authorized for this write. | Park. |
| `unavailable` | outcome (`retry-later`) | Temporarily unable to decide. | Resend later. |
| `base-expired` | outcome | The base version is at or below the retention horizon and the document no longer exists. | Park; forget the base, so a new edit recreates the document (section 4). |
| `group-aborted` | outcome (`retry-later`) | Another member of the same dependency group was not accepted. | Keep pending; resend with the group (section 4.1). |
| `group-failed` | replica only | Another member of the group was kept as a conflict or rejected. | Park until that member is resolved or retried. |
| `groups-unsupported` | replica only | The authority does not advertise `groups`. | Park; never send the group piecemeal. |
| `reset-required` | request error | Checkpoint unusable; `reason` is `epoch`, `scope-changed` or `expired`. | Reset (section 6.1). |
| `upgrade-required` | request error | Unsupported protocol or schema version. | Stop syncing; upgrade. |
| `payload-too-large` | request error | Request over limits. | Use smaller batches. |
| `rate-limited` | request error | Too many requests. | Wait (`Retry-After`). |
| `unauthorized` | request error | Missing or expired credentials. | Renew credentials. |

## 8. HTTP binding

- `POST {base}/collections/{collection}/pull` with a pull request body; `POST {base}/collections/{collection}/push`
  with a push request body; `application/json; charset=utf-8`.
- Headers `Bsync-Protocol: 1` and `Bsync-Schema: {application schema id}` on every request.
- `Content-Type: application/json` is required (`415` otherwise).
- Request errors use RFC 9457 `application/problem+json` with a `code` member from section 7. Status codes:
  `400` `invalid-request` and `upgrade-required`, `401` `unauthorized`, `403` `forbidden`, `409`
  `reset-required`, `413` `payload-too-large`, `429` `rate-limited`, `503` `unavailable` (with
  `Retry-After` when known). Clients act on `code`; the status is informative. A `reset-required` problem
  carries a `reason` member (section 6.1); clients treat an absent or unknown reason as `epoch`.
- A missing `Bsync-Protocol` header is `invalid-request`; an unsupported protocol or schema is
  `upgrade-required`. Both are refused before the body is read.
- The body size limit is enforced while reading, independently of `Content-Length`.
- Responses carry `Cache-Control: no-store`.
- **Hints (optional).** `GET {base}/collections/{collection}/hints` with the same headers returns
  `text/event-stream`. The server sends `event: resync` once when the stream opens and again after commits in
  the caller's scope, plus comment lines as keep-alives. Events carry no document ids or data; a client that
  receives one pulls. Hints are best effort: clients MUST NOT rely on them for correctness and MUST keep
  reconciling on their own schedule (I13). A server without hints answers `404`.
- Service workers MUST NOT proxy sync requests. In particular, a proxied hint stream keeps the old worker busy,
  and some browsers then never let a new version take over.
- Limits (maximum operations per push, maximum page size) are advertised in every pull response (`limits`,
  section 3.2) and enforced with `payload-too-large`. The maximum body size is enforced but not advertised.
- Scope and principal are taken from the authenticated request, never from the body (ADR-010).
- **Pull batches (optional, feature `pull-batch`).** A server that maps several collections as one group
  advertises `pull-batch` (and `hints-multiplex`) in their pull responses and accepts
  `POST {base}/pull` with `{ "collections": { "{collection}": {pull request}, ... } }`. It answers `200` with
  `{ "results": { "{collection}": { "status": 200, "result": {pull response} } | { "status": n, "problem": {problem} } } }`:
  each collection is pulled exactly as its own endpoint would, with the same status codes and problem members, and one
  collection's failure does not affect the others. Authentication, headers and body limits apply to the batch request
  as a whole. Clients send a collection at most once per batch and use batches only after the feature was advertised;
  a server without it answers `404`, and clients then pull per collection.
- **Blobs (optional).** Content named by documents (attachments) is transferred beside the protocol, under its own
  prefix (`{blobs}`, by default `{base}/blobs`), with the same authentication and scope. `{sha256}` is 64 lowercase
  hexadecimal characters; anything else is `400`. Responses are JSON `{ "received": n, "complete": bool }`, plus an
  optional `uploadUrl`, with `Cache-Control: no-store`; refusals with a code use `application/problem+json`.
  - `POST {blobs}/{sha256}/uploads?size=n` starts or resumes an upload: `complete: true` when the caller's scope
    already holds the content, else how many bytes the server holds. When the server's store offers it and nothing is
    held yet, `uploadUrl` is a short-lived absolute URL to which the client MAY send the whole content in one `PUT`
    (without the sync credentials) instead of chunks; clients that ignore it upload in chunks. `413`
    `blob-too-large` above the server's limit.
  - `PUT {blobs}/{sha256}/uploads/{offset}` appends the body if the server holds exactly `offset` bytes, else `409`
    with the real `received`. Bytes that arrive before a connection drops are kept.
  - `POST {blobs}/{sha256}/uploads/finish` verifies the hash of what was received (in chunks or at `uploadUrl`) and
    records that the caller's scope holds the content: `complete: true`. A mismatch discards the upload: `422`
    `blob-hash-mismatch`. Repeating a finish is harmless. The object is stored once per hash, whichever scopes upload it.
  - `GET {blobs}/{sha256}` returns the content with range support, or a temporary redirect to a presigned URL that
    serves it (also with ranges). A caller who may not read it gets `404`, whether or not the content exists.

## 9. Versioning

This is protocol version 1. A change that alters the meaning of an existing member or adds a required
member requires a new version. Adding optional response members is compatible; receivers MUST ignore
unknown envelope members.
